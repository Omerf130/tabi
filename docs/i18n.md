# Internationalization (i18n)

Tabi supports Hebrew and English interface localization using `next-intl`.

## Supported locales

| App locale | HTML `lang` | Direction | Intl display locale |
|------------|-------------|-----------|---------------------|
| `he` (default) | `he` | `rtl` | `he-IL` |
| `en` | `en` | `ltr` | `en-US` |

## Ownership

- **User locale** lives on `User.locale` in MongoDB.
- Locale is **user-scoped**, not trip-scoped.
- Two members of the same trip may use different interface languages.
- Phrasebook destination language (`src/features/language/`) is separate from UI locale.

## Locale resolution invariant

`User.locale` is the persistent canonical preference.

`tabi_locale` is a synchronized SSR projection of `User.locale`. It is **not** a second independent preference.

Resolution order for ordinary SSR requests:

1. Valid `tabi_locale` cookie → use directly for messages, `lang`, and `dir`.
2. Missing/invalid cookie + authenticated session → proxy redirects once to `/auth/sync-locale`, which sets `tabi_locale` from MongoDB and redirects back. Layout recovery may read MongoDB for the current render only; it must **not** write cookies.
3. Unauthenticated request → valid cookie if present, otherwise default `he`.

Sync points:

- Login / session creation
- Google OAuth session creation
- Language preference change
- One-time `/auth/sync-locale` recovery redirect when session exists but `tabi_locale` is missing/invalid

Cookie writes are allowed only in Server Actions, Route Handlers, and proxy responses — never during layout/page Server Component render.

Do **not** query MongoDB on every root layout render just to compare `User.locale` against the cookie.

## next-intl setup

- Library: `next-intl`
- Request config: `src/i18n/request.ts`
- Messages: `messages/he.json`, `messages/en.json`
- No locale URL prefixes (`/he/app/...` is not used)
- No next-intl routing middleware; existing auth `src/proxy.ts` remains separate

Root layout resolves locale server-side and sets `<html lang dir>` plus `NextIntlClientProvider`.

## Message namespaces

Use feature namespaces, not one giant flat file:

- `Navigation`
- `TripHeader`
- `AccountMenu`
- `TripManagement`
- `Common`
- `Home`
- `Itinerary`
- `Activity`
- `Errors`

Server components:

```ts
const t = await getTranslations("Navigation");
```

Client components:

```ts
const t = useTranslations("Navigation");
```

## Migrating a feature

1. Add strings to both `messages/he.json` and `messages/en.json` under a feature namespace.
2. Replace hardcoded UI copy with `getTranslations` (server) or `useTranslations` (client).
3. Keep routes and domain values language-independent.
4. Prefer CSS logical properties in touched styles.
5. Use `dir="auto"` for mixed-script user/destination content.

## RTL / LTR rules

- Document direction comes from resolved app locale.
- Prefer logical CSS (`margin-inline`, `padding-inline`, `inset-inline`, `border-inline`).
- Flip directional chevrons/back icons with `[dir="rtl"]` / `html[dir="ltr"]`; do not duplicate icon assets per language.
- Do not force mixed destination content (e.g. `Tokyo`, `東京`, `TLV → NRT`) into incorrect visual order.

## Formatting

Canonical domain dates remain `YYYY-MM-DD`.

Display formatting should use:

```ts
import { formatAppDate, formatAppNumber } from "@/features/i18n/formatting";
```

English display locale for V1 is `en-US`.

## Server errors

New localized flows should return stable error codes from server actions:

```ts
return { errorCode: "invalid_locale" };
```

Map codes to UI copy with translations in the rendering layer. Avoid adding new hardcoded Hebrew/English server messages.

## Incremental migration status

S2 migrated shared authenticated shell copy only (primary nav, trip header actions, account footer, manage intro, language switcher).

S2B migrated Trip Home and Itinerary feature UI (journeys, countdown, reminders, activity forms, day actions, plural formatters, place search labels).

Other feature pages may still contain Hebrew-only copy until their own migration phase.

Public/auth screens (Welcome, Login, Register, My Trips, Create Trip) intentionally retain their current English LTR islands.

## PWA compatibility

Future PWA manifest `lang` can derive from `User.locale`. Stable unprefixed routes remain compatible with service worker caching.
